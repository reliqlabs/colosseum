**Clause-by-clause:**

- **B1**: `acquire` is a textbook check-then-act race. The liveness check (api.rs:52-58) runs under a read lock that is dropped at line 58; the insert at line 68 takes a fresh write lock and blindly overwrites whatever is in the map. Two concurrent acquirers of one resource both pass the check, both allocate tokens, both get `Ok`; the second insert clobbers the first grant. Worse, insert order can invert token order: A allocates token 1, B allocates token 2, B inserts, A inserts last, so the stored lease carries token 1 while token 2 is at large, and the fencing layer will reject the active holder. Same shape at line 46: the capacity check races with concurrent inserts, so the map can exceed `max_leases`.
- **B2**: api.rs:49 does `ttl_ms.max(1)`, exactly the silent widening B2 forbids. `LeaseError::ZeroTtl` is never constructed anywhere (symptom, not a separate finding). Renew repeats the widening at line 88.
- **B3**: lease.rs:48 uses `now_ms <= expires_at_ms`. At `now == deadline` the lease should be expired; instead it still blocks `acquire` with `Held` and escapes `reap`. Since callers drive time in discrete ms, equality is routinely reachable.
- **B4**: the allocator is per-resource (tokens.rs:20) and `forget` (tokens.rs:27) is called on both release (api.rs:101) and reap (api.rs:113), so a release/re-acquire cycle restarts the resource at token 1. B4 names this exact path as forbidden, and tokens.rs's own doc comment ("never be handed out twice over the manager's lifetime") contradicts the code. Separately, per-resource counters issue the same value for different resources, so tokens are not unique over the manager's lifetime even without a release.
- **B5**: api.rs:85 has the polarity inverted: `lease.token == token` returns `BadToken`, so the rightful holder can never renew and any wrong token succeeds and moves the deadline. B5 requires a non-matching token to change nothing.
- **B6**: lease.rs:36 computes `now_ms + ttl_ms` unchecked; release builds wrap into a past deadline (debug builds panic), and `TtlOverflow` is never produced despite `Lease::new` returning `Result` and its doc claiming refusal. Renew (api.rs:88) uses `saturating_add`, which clamps; B6 forbids clamping too.
- **B7**: reaper.rs:27 discards the notifier result with `let _ =`. The lease is removed before the notice outcome is known and counted as collected regardless; `reap` can never surface `NotifyFailed`.
- **B8**: `release` frees the lease and the token counter but not the waiters (reap does, at api.rs:112, so the omission at release is not a design choice). And `register_waiter` accepts registrations for resources with no lease; nothing ever frees those entries, which is the exact accumulation path B8 rules out. A `register_waiter` racing a `reap` lands in the same orphaned state.

**Intent-unnamed production defect**: `reap` runs the caller-supplied `Notifier` while holding the `leases` write lock (api.rs:107-108, callback at reaper.rs:27). A slow notifier stalls every manager operation; a notifier that reenters the manager (e.g. calls `register_waiter` or `acquire`) self-deadlocks, since parking_lot locks are not reentrant.

**Noted but not filed**: `acquire` over an expired lease dispossesses the old holder with no notification; the intent only mandates notice on the reap path, so this is a gray area. `ZeroTtl` and `TtlOverflow` being unreachable, and `Lease::new`'s never-failing `Result`, are symptoms of filed findings, not separate dead code. Lock ordering across operations is otherwise consistent (leases, then waiters, then tokens), so no ordering deadlock beyond the reentrancy hazard above.
